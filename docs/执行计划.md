## 目标与原则

交付可独立运行的素材制作网站：浏览模板、上传图片、提交任务、由 Java 后台依次执行「素材检查 → 模拟生成 → 结果整理」，并按用户查看历史、失败原因和结果图片。以题干 R-01～R-14 为验收清单，优先保证业务闭环、异步状态正确和容器可验收，再做视觉完善。

- 后端负责业务执行、任务状态与历史持久化；Next.js 负责页面和前端异步状态。
- 每个阶段有服务端可查询的独立执行边界；查询请求只读，不推进任务。
- 上传、提交、后台执行和查询异常使用不同状态；多个任务按 ID 独立更新。
- 不引入真实 AI、消息队列、Redis 或题外管理后台，除非后续证据表明确有必要。
- 每完成一个阶段，记录实际投入、取舍、验证结果与尚未验证的边界，供最终 README 使用。

## P1：后端业务闭环（最高实现优先级）

1. **模板与素材（R-01～R-03）：** Java 从数据库种子数据读取至少 3 类模板，覆盖 1 张和 2 张以上图片要求；封面可访问。上传文件落盘，校验实际图片类型、大小、可解码性及用户归属；提交时再次检查模板要求和素材有效性。
2. **受理与执行（R-04～R-06）：** 受理事务只做校验、创建任务及关联记录，返回后由 Java 工作器执行。优先选择 MySQL `QUEUED` 任务 + 单实例串行工作器：便于展示排队，避免「数据库已提交但线程池投递失败」留下永久等待任务。阶段开始、成功或失败分别短事务落库，模拟延迟不占用数据库事务。
3. **失败与结果（R-05～R-06）：** 在指定阶段可重复触发失败，并可调整三个阶段耗时；失败后停止后续步骤、记录可读原因。成功后写入真实可预览的本地结果图或上传图的独立持久化副本，任务和结果关联一致。查询接口只读；终态不可回退。
4. **身份与历史（R-09～R-10）：** Java 会话识别演示用户；任务、素材及结果按用户隔离。历史按创建时间排序，避免固定条数截断而无翻页途径。刷新后从 MySQL 恢复记录。

**P1 完成标准：** 单任务成功、三个指定阶段失败、多任务排队、跨用户隔离、刷新后历史读取均可从接口验证。明确记录进程重启时 `RUNNING` 和 `QUEUED` 的处理策略；若不做自动恢复，应让遗留状态可解释，不宣称已恢复执行。

## P2：前端页面与异步状态

1. **模板列表及详情（R-02、R-03、R-11）：** 分类和卡片来自 Java；详情按模板要求渲染上传位。提供加载、空数据、404 和请求失败反馈；支持选择、预览、替换、移除、上传进度/失败，提交前校验数量、类型和大小。
2. **提交与多任务（R-07、R-08）：** 上传中和提交中禁用重复提交；受理成功立即切换到任务等待/处理中，允许继续创建。以用户 ID、任务 ID 隔离查询缓存和状态，防止旧响应覆盖新用户或其他任务。
3. **历史与恢复（R-07～R-09）：** 展示时间、状态、阶段、失败原因及结果预览。只自动跟踪未结束任务，任务终态停止跟踪，没有活跃任务时停止轮询；离开页面或切换用户时取消相关请求。查询失败保留最后一次成功数据并提供手动重试，不把网络错误写成任务失败。
4. **基本可用性（R-11）：** 对照 UI-01～UI-03 的主要布局做桌面页面，小屏可完成操作；按钮和上传控件有语义标签、键盘焦点与清晰反馈。

**P2 完成标准：** 连续创建两个以上任务，各自状态不串扰；刷新后恢复；断开任务查询时保留旧状态，恢复后可继续读取；终态后网络面板不再持续轮询。

### 2. 数据模型与约束

以下是逻辑字段标准，实际 SQL 类型与命名可在 P0 定稿，但不得缺少关键约束。统一使用 UUID 字符串作为公开 ID；数据库时间使用 UTC，接口返回带时区的 ISO 8601 字符串；页面按浏览器时区显示。

| 表 | 关键字段 | 必要约束/索引 |
| --- | --- | --- |
| `users` | `id`、`demo_key`、`display_name`、`created_at` | `demo_key` 唯一；只创建 Alice/Bob 等演示身份。 |
| `sessions` | `token_hash`、`user_id`、`expires_at`、`created_at` | 仅保存令牌摘要；`user_id` 外键；过期或退出后不可再使用。 |
| `templates` | `id`、`title`、`category`、`description`、`cover_path`、`required_image_count`、`accepted_mime_types`、`max_file_size_bytes` | 数量必须 >0；至少 3 类、同时有单图和多图模板；种子迁移可重复部署。 |
| `assets` | `id`、`user_id`、`storage_path`、`mime_type`、`size_bytes`、`width`、`height`、`purpose`、`created_at` | 路径由服务端生成；`purpose` 区分上传与结果；索引 `user_id,created_at`。 |
| `tasks` | `id`、`user_id`、`template_id`、`template_title_snapshot`、`status`、`current_stage`、`simulation_json`、`result_asset_id`、`failed_stage`、`error_code`、`error_message`、`created_at`、`started_at`、`finished_at`、`version` | 索引 `status,created_at` 供工作器领取，索引 `user_id,created_at,id` 供历史查询；模板标题快照保证历史展示稳定。 |
| `task_assets` | `task_id`、`asset_id`、`position` | 联合唯一约束 `task_id,position` 与 `task_id,asset_id`；保留上传顺序。 |
| `task_steps` | `task_id`、`stage`、`status`、`started_at`、`finished_at`、`error_message` | 主键 `task_id,stage`；任务受理时插入三个 `PENDING` 步骤。 |

数据库结构通过 `V1__schema.sql` 等迁移文件建立，模板/用户种子数据用后续迁移或幂等 seeder。已发布迁移不回写；升级新增版本文件。`version` 在每次任务状态/阶段变化时递增，供前端拒绝过期响应。模板被历史任务引用后，即使后续调整模板，历史仍使用 `template_title_snapshot` 和当时的素材要求/模拟配置快照解释任务。

### 3. HTTP 接口契约

所有浏览器请求走同源 `/api/**`；Next.js Route Handler 只代理请求、响应、Cookie 和状态码到 Java，Java 负责鉴权与业务。代理必须透传 multipart 上传、`Set-Cookie`、图片 `Content-Type`、4xx/5xx 和取消信号；后端地址仅来自服务端环境变量，不进入浏览器包。前端 `fetch` 不从页面拼装任意后端 URL。

| 方法与路径 | 请求 | 成功响应 | 关键错误 |
| --- | --- | --- | --- |
| `GET /api/templates?category=` | 分类可省略 | 模板数组，字段含 `id,title,category,coverUrl,description,requiredImageCount,acceptedMimeTypes,maxFileSizeBytes` | 503/网络失败显示可重试错误，空数组显示空状态。 |
| `GET /api/templates/{id}` | 路径 ID | 单个模板 | 404 显示不存在，不无限重试。 |
| `GET /api/demo-users` | 无 | 演示用户列表；不包含令牌 | 演示模式关闭时 404/403。 |
| `POST /api/session` | `{ "demoUserKey": "alice" }` | 用户摘要 + `HttpOnly` Cookie | 未知用户 400/404；不接受请求中的 `userId` 作为资源归属。 |
| `GET /api/session` / `DELETE /api/session` | Cookie | 当前用户 / 204 清 Cookie | 无有效会话 401。 |
| `POST /api/assets` | `multipart/form-data`：`templateId`、`file` | 201 `{id,previewUrl,mimeType,sizeBytes,width,height}` | 400 参数、401 未登录、413 超大小、415 非法图片。 |
| `GET /api/assets/{id}/content` | Cookie | 仅本人可读的图片流 | 不存在或非本人均 404；响应使用 `Cache-Control: private, no-store`。 |
| `POST /api/tasks` | `{templateId,assetIds,simulation?}` | **202**，任务快照及 `Location: /api/tasks/{id}` | 400 参数、401 身份、404 模板或素材、409 冲突；响应不等待三个阶段。 |
| `GET /api/tasks/{id}` | Cookie | 单个任务快照及 `steps` | 非本人或不存在均 404；只读。 |
| `GET /api/tasks` | Cookie | 当前用户全部历史，按 `createdAt DESC,id DESC` | 当前演示数据量小，先不截断；数据增长后的分页作为已知限制记录。 |

建议任务快照：`id,templateId,templateTitle,status,stage,createdAt,startedAt,finishedAt,resultUrl,failedStage,errorCode,errorMessage,version,steps`。`steps` 每项包含 `stage,status,startedAt,finishedAt,errorMessage`。未产生的值明确返回 `null`，不用空字符串伪装。统一错误体为 `{code,message,traceId}`；客户端显示可理解的 `message`，服务端日志按 `traceId` 排查，不向接口暴露磁盘路径或堆栈。

`simulation` 只在 `DEMO_MODE=true` 时允许，格式为 `{failAtStage: null|"ASSET_CHECK"|"GENERATE"|"FINALIZE", stageDelayMs: {ASSET_CHECK?: number, GENERATE?: number, FINALIZE?: number}}`。服务端验证每个延迟为 0～30000 毫秒整数，缺省值读取环境配置，在**受理时快照到任务**。同一请求指定阶段即确定失败，不使用随机数；README 给出带演示会话的成功与三阶段失败调用方法。正式页面可不展示模拟控制。

```

}
```

前端与 Java 使用同一份手工维护的契约文档和 TypeScript 类型；接口字段变化必须同时更新 Java DTO、前端类型、测试样例和 README。`202` 响应展示受理状态；最终成功/失败只能通过后续查询得知。

### 4. Java 异步工作器与状态机

```text
POST /api/tasks：验证模板/素材/用户 → 单个短事务插入 QUEUED 任务、素材关联、3 个 PENDING 步骤 → 返回 202
Java 定时工作器：领取最早 QUEUED → RUNNING
  ASSET_CHECK：RUNNING → SUCCEEDED
  GENERATE：RUNNING → SUCCEEDED
  FINALIZE：RUNNING → 生成/保存结果 → SUCCEEDED，同时任务 SUCCEEDED
任一步异常：该步骤 FAILED、后续步骤 SKIPPED、任务 FAILED，写入失败阶段和原因
```

任务整体状态只允许 `QUEUED → RUNNING → SUCCEEDED/FAILED`，步骤状态只允许 `PENDING → RUNNING → SUCCEEDED/FAILED`；失败步骤之后的步骤从 `PENDING → SKIPPED`。`SUCCEEDED` 和 `FAILED` 为终态，任何查询或重复领取都不能回退。`current_stage` 表示当前/最后执行阶段；任务刚受理时为 `null`，成功后保留 `FINALIZE`，不使用它推断整体成功。

工作器默认单实例、单调度线程，约 500 毫秒扫描一次队首任务；用 `UPDATE tasks SET status='RUNNING' ... WHERE id=? AND status='QUEUED'` 的受影响行数完成原子领取，重复触发时只有一个执行者进入流水线。`startStage`、`completeStage`、`failStage` 均通过独立 Spring Bean 的 `@Transactional` 方法写任务与步骤，避免同类内部调用绕过事务代理。每步的 `sleep` 和文件操作在事务外，事务内只做短暂状态修改。SQL 更新必须带预期状态条件并检查受影响行数；结果关联、最终步骤成功与任务成功在同一数据库事务提交。

任务受理前验证数量与去重、模板允许的 MIME/大小、素材归属和文件可读性；执行到 `ASSET_CHECK` 时再次检查文件存在且可解码，以演示受理后文件异常的失败边界。模拟失败先于该阶段的真实操作触发，失败后的步骤不得执行。预期错误写稳定 `errorCode` 和中文 `errorMessage`；非预期异常记录日志，客户端只看安全的概括信息。若失败状态写库也遇到数据库故障，日志必须包含任务 ID，README 说明需在数据库恢复后重启后端进行收敛。

**重启策略：** 启动时在工作器开始轮询前，将遗留 `RUNNING` 任务标为 `FAILED/PROCESS_INTERRUPTED`，保留中断阶段并将仍在运行的步骤标失败；`QUEUED` 保留并继续等待领取。不会从阶段中间继续执行。结果文件已落盘但事务未提交时可能留下孤儿文件，不能错误地宣称任务成功；清理孤儿文件可列为后续工作。该策略只针对单 Java 实例，不能把它描述成多实例故障转移。

### 5. 上传、结果文件与身份隔离

- 文件名使用随机 ID 和服务端确认的扩展名，数据库只保存相对路径；原始文件名只作展示，不参与文件系统路径。解析路径时确认规范化后的目标仍在存储根目录内，避免 `../` 路径逃逸。
- 接受 JPEG/PNG、单张不超过 5 MiB；不仅检查浏览器 MIME/扩展名，还检查文件签名与实际解码，并设置像素上限（建议 2400 万像素），拒绝空文件和无法读取的图片。模板可以进一步收紧 MIME 或大小要求。
- 上传先写临时文件、验证后原子移动到持久目录，再写 `assets` 行；若数据库插入失败，删除本次新文件。替换/移除上传位只改变尚未提交的前端选择，已上传但未被任务引用的文件暂不立即删除，作为已知限制。
- 结果整理不需真实 AI。为保证可预览，最小实现可将第一张有效上传图重新编码或复制为独立结果文件；若时间允许再做简单拼贴。先准备文件，再在事务中插入结果素材并将任务改为成功；若事务失败，尽力删除新文件。
- 演示会话由 Java 签发高熵随机令牌，Cookie 设 `HttpOnly; SameSite=Lax; Path=/`，本地 HTTP 下 `Secure=false`，HTTPS 部署下必须为 `true`。数据库只存令牌摘要与过期时间。所有任务、上传与结果访问从会话取得用户，不信任客户端传来的用户 ID。公开封面与私有图片使用不同读取路径；读取他人任务、素材或结果统一返回 404。

### 6. Next.js 页面与请求生命周期

路由建议：`/` 为模板列表，`/templates/[id]` 为详情及上传/提交，`/history` 为个人历史；顶部统一提供演示用户切换。页面结构以参考 UI 的列表、详情左侧制作/右侧任务、历史卡片为依据，小屏改为纵向排列。所有可点击元素使用 `button`/`a`，上传位绑定可见标签或 `aria-label`，图标按钮标明作用，弹窗关闭后恢复焦点。

上传位以模板 ID 和槽位索引管理：`empty → validating → uploading → ready`，失败转为 `error`；每个槽位保留独立的本地预览 URL、服务端素材 ID、进度与错误。替换时取消旧上传请求并使旧请求结果失效；移除时撤销本地 object URL。只有全部槽位 `ready` 且素材数满足模板时允许提交。提交按钮的 `submitting` 只持续到收到 202 或请求失败；受理后立刻清理提交状态并将任务加入记录，允许新任务提交。

任务查询统一使用 TanStack Query 5，历史缓存键为 `['private', userId, 'tasks']`，受理任务快照键为 `['private', userId, 'task', taskId]`。列表响应逐条按 ID 合并，比较 `version`：低版本响应不覆盖高版本，终态不回退为非终态；新提交的任务先由 202 响应写入缓存，随后刷新历史。所有 query function 将 TanStack 提供的 `AbortSignal` 传给 `fetch`；切换用户时取消旧用户查询并清除旧用户个人缓存，避免旧响应覆盖新用户。

当前实现使用完整历史列表动态轮询：列表含任意 `QUEUED/RUNNING` 时约每 2 秒查询一次，否则 `refetchInterval` 返回 `false`。Java 返回全部历史，前端不截断活跃任务；每条任务仍按 ID/版本独立合并。TanStack 的 [`refetchInterval` 函数](https://tanstack.com/query/latest/docs/framework/react/guides/polling)支持按查询状态停止轮询。全局跟踪器允许在站内切页时继续更新；切换用户会取消并清理旧用户请求。查询失败时保留最后成功数据、暂停定时查询并显示“恢复查询”，不改写任务的 `status`；如果此前没有数据则显示整块错误状态。身份返回明确 401 才清会话，网络 503 不当作退出登录。

前端要区分五类反馈：上传错误、提交错误、任务业务失败、状态查询错误、图片预览错误。提交 POST 超时可能出现“服务端已受理但前端不知道”的边界；本题不要求幂等，先通过刷新历史查找新任务并在 README 说明，避免直接建议用户盲目重复提交。若实施时间充足，再用 `clientRequestId` + 用户唯一索引实现受理幂等。

### 8. Compose、配置与部署回滚

`db`、`backend`、`frontend` 三服务；`db` 有 MySQL 健康检查，`backend` 在 `db: service_healthy` 后启动，`frontend` 在后端健康后启动。[Compose 官方文档](https://docs.docker.com/compose/how-tos/startup-order)说明 `service_healthy` 会等待依赖的健康检查通过。只对宿主机开放前端 3000 端口；Java 和 MySQL 通过 Compose 内部网络互联。`mysql-data` 与 `asset-data` 使用命名卷。前端可用 [Next.js standalone 输出](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)缩小运行镜像，并核对静态资源是否一同复制。

环境变量至少包括 `SPRING_DATASOURCE_URL/USERNAME/PASSWORD`、`STORAGE_ROOT`、`DEMO_MODE`、三个阶段默认延迟、`JAVA_API_ORIGIN`、`SESSION_COOKIE_SECURE`。`.env.example` 仅放本地演示值，真实 `.env` 加入 `.gitignore`；README 解释构建期与运行期变量差异。健康接口只证明服务可用，不能替代业务链路测试。

部署步骤：固定验收 commit/镜像版本 → 备份数据库与文件卷 → `docker compose up --build -d --wait` → 检查健康和一条实际成功/失败链路。回滚步骤：确认迁移是否向后兼容 → 恢复前一镜像/commit → 必要时成对恢复数据库与文件卷 → 再验收历史结果。不得用 `docker compose down -v` 代替回滚；它会删除演示数据。单实例、本地卷、未做自动断点续跑等限制必须在 README 明示。
